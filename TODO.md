## The rule: `v1` takes bug fixes only

**`v1.11.0` was the last feature release, and there will be no `v1.12.0`: every remaining `v1` release is a patch.** Three reasons, and the first is the one that decides it:

- **A `v1` feature is work with a scheduled deletion date.** The centerpiece of `2.0.0` is a ground-up rewrite onto Cloudflare (below): Rails becomes Hono, Next becomes Nuxt. Anything built in `api/` or `web/` from here has to be built a second time in a stack that does not exist yet, so a feature added now is paid for twice and demoed once.
- **The app is finished for the search that is actually running.** The north star is one user, and he has the tool: capture, pipeline, follow-ups, the takeability constraints, the daily driver. Every remaining idea in this file pays off *after* the search closes, which is precisely what the `2.0.0` trigger encodes.
- **Cadence.** Every merge under a watch path is a Railway deploy, and each PR burns two CI runs (`CLAUDE.md` § Branching & PRs). A frozen feature surface is what makes the one-PR-per-day rule cheap instead of something to work around.

**The admission test, applied to anything proposed for `v1`:** does it make something the app already does work correctly, or stop something it already does from being abused? If yes, it may ship, and it will be a patch by the mechanical test (no migration, no `v1` contract broken, no new capability). If it adds a capability, however small and however tempting, it is `2.0.0` work and waits for the trigger. Security fixes, dependency bumps, and CI chores pass on the same reading: none of them is a capability.

**The freeze does not gate the `2.0.0` cluster; it is what fills it.** What is frozen is shipping features into the current stack, not wanting them. An idea that arrives tomorrow gets written down there, not argued into a patch.

## Standing rules

Three rules that outlive the releases that produced them. The freeze retires the first two from `v1` duty (no patch adds a column or a field), so their live consumer is the `2.0.0` schema work and the record of why the existing columns are shaped as they are; other documents cite them here by name, which is why they stay.

- **The trap that breaks a minor whenever it adds a column: the column must be nullable or defaulted.** A `NOT NULL` column with no default means the previous image's `INSERT`s fail against the new database, and by the mechanical test that quietly turns a minor into a **major**. It is the only way a minor accidentally violates its own versioning. `v1.6.0`'s two new tables (`credentials`, `push_subscriptions`), `v1.8.0`'s eight `applications` columns, and `v1.9.0`'s visa/hiring/timezone fields all shipped clean under it. A column shipped loose under this rule is deferred, not forgotten: the `2.0.0` schema re-optimization item below owns the tightening pass, so the debt has an address.
- **Field admission test, for any new per-application column** (channel, agency, comp structure, language level, hiring entity, timezone, all of them): it must be **captured at prefill time by `UrlPrefillService`, or cost near-zero manual entry**. The app has one user, and a field he stops filling in after the fifth application is dead schema plus form friction. This bites next on `2.0.0`'s `positions` entity and the tightening pass; it stays here as the test every future field is measured against.
- **Perishable-facts refresh rule, for every Japan-market item.** Each embeds perishable external facts: fee schedules, processing times, survey medians. A career tool that confidently states last year's rules is worse than one that says nothing, so each such item must state its **annual refresh cost** when it is scoped, and the sum of those lines is a real cap on how many of these a solo maintainer can ship. The shipped ones carry their cost already (the `holidays` gem is one `bundle update`; `Visa::COE_LEAD_TIME_DAYS` and the HSP point table are sourced constants). The rule governs the `2.0.0` career-intelligence item next, which already budgets this way ("one data-entry session a year").

- [ ] **`next dev` crashes even with a 4 GB heap** (`--max-old-space-size=4096`, added in v1.1.1). **Diagnosed 2026-07-11**: it is a **V8 heap leak in the `next-server` process**, not native/Rust memory and not the OS: 30 days of journal show zero OOM-killer or systemd-oomd kills, and an instrumented run (`--report-on-signal` diagnostic reports + RSS sampling) showed V8 `usedMemory` tracking RSS growth ~1:1 while the native baseline stayed a flat ~0.8–1.5 GB. Retention is monotonic and unbounded: ~239 MB V8 heap at boot, ~541 MB after warming the ten public routes, then **~40–60 MB retained per HMR rebuild** (3.1 GB used / 5.8 GB RSS after 30 scripted edits, `detachedContextCount` 0 throughout). So raising `--max-old-space-size` only postpones the `JavaScript heap out of memory` abort: 4 GB dies in a normal editing session; 8 GB (the machine has 29 GB) buys a longer one, nothing more. The behaviour matches upstream discussion **#93451** (unbounded growth after HMR edits, ~7 GB, open and unresolved as of 2026-07); issue #85290 (404 → infinite compile loop) does **not** reproduce here. Warm boot-to-ready is ~5 s with the Turbopack FS cache, so a periodic dev-server restart is a viable stopgap.
  - **Next actions:** the stopgap is **done** (`cf7cd8d`); the dev script already runs with an 8 GB heap and `--heapsnapshot-near-heap-limit=1` (allowed there; `--trace-gc` is not), so the next real crash writes the heap snapshot upstream wants. What remains: file on #93451/new issue with that snapshot, and restart the server when it gets slow. One unexplained datum for the upstream report: V8 heap also jumped ~1.6 GB across the 404 phase and a 45 s idle window: growth without edits, so renders (every route is dynamic here: the CSP-nonce `await connection()`) retain memory too, not just compiles; the three-family font setup compiling into every layout pass may be a multiplier (production loads five variable slices, not ~15 static files).
  - **The rewrite is not the fix, and must not be treated as one.** Nuxt/Nitro is a different dev server with a different leak profile, so this outlives the freeze either way: until the trigger fires it is a daily annoyance with a working stopgap, and after it fires the upstream report is still the only thing that helps anyone else.

### The centerpiece: rewrite to Hono + Nuxt on Cloudflare *(item one the moment the search succeeds)*

Decided 2026-07-22. What used to read as three scattered items in this cluster (a Nuxt "north star", a Hono backend, and a $0-hosting move off Railway) is **one move**, because it settles three bets at once and they share a single trigger:

- **Specialty signal (the portfolio bet).** Depth over breadth: rather than staying one more generic Next.js tracker, lean all the way into the framework the author already contributes to, so the flagship app *is* the flagship of a Vue/Nuxt-specialist-and-OSS-contributor identity.
- **$0 hosting (the cost bet).** Railway has **no free tier** (Hobby is a $5/month minimum), so today's ~$6.30/month (api ~$4.40 of it at a 0.44 GB average, measured 2026-07-20) only zeroes by leaving Railway entirely, *both* services. This rewrite lands both halves on Cloudflare's free tier by construction. Same trigger-shape as the Cloudflare-proxy revisit: the always-warm-demo rationale (the repo's job is Tokyo hiring signal; its first hit is a screener clicking the link) expires the moment the job lands, and cost wins.
- **Serverless modernization.** Cold starts stop mattering once nobody is being impressed by a live demo, so the trade-offs that would hurt a portfolio piece are free here.

The target stack, verified free as of 2026-07-22:

- **Backend: Rails → Hono on Cloudflare Workers.** ActiveRecord is replaced by a TS query layer (Drizzle or Kysely over `pg`), so the schema survives but the ORM does not. Solid Queue's persistent poller moves to Cloudflare Cron Triggers. The two invariants port as *shape*, not as a rewrite of the rules: `ApplicationFSM::TRANSITIONS` stays the single copy of the transition table (now in TS), and status changes still route through one transition service, never direct attribute writes.
- **Frontend: Next → Nuxt.** The single largest work item anywhere in this file: all of `web/`, the i18n navigation wrapper, the CSP-nonce `proxy.ts` guard, every component and form. Nuxt/Nitro's **native Cloudflare preset** makes the deploy trivial and is the cleaner of the two paths, versus keeping Next and shipping it through the OpenNext `@opennextjs/cloudflare` adapter.
- **Data: Postgres stays, the host changes.** Neon or Supabase free tier, fronted by **Cloudflare Hyperdrive** (connection pooler + query cache: free, no egress charge, `node-postgres` is its recommended driver, so the classic serverless connection-exhaustion problem is exactly what Hyperdrive absorbs). Two rejected paths recorded so they are not re-litigated: **D1 is SQLite, not Postgres**, so it is not a drop-in for this schema; and Cloudflare's *native* managed Postgres (via PlanetScale, billed through the Cloudflare account, June 2026) is **paid**, the convenience path, not the free one.
- **Public domain: `kk.chairulakmal.com`** (decided 2026-07-22), bound to the Worker as a custom-domain route. A subdomain of the personal apex on purpose: it puts the author's name as the primary information in the link, so a screener sees whose project this is before the page loads, the portfolio signal a standalone `karirkalyan.com` would throw away. It is also free and consistent with the $0 goal (one DNS record on a zone already run), and the terse `kk` is chosen over a self-documenting `karirkalyan.` slug precisely to keep the name the dominant token. **Prerequisite, and the one thing that inverts the signal:** `chairulakmal.com` itself must resolve to a real personal site or CV, because a screener will strip `kk.` to see who the author is, and a parked or 404 apex reads worse than no custom domain at all. A dedicated product domain is warranted only on a pivot to external users, which the north star rejects.

**Why the trigger and not now:** the current search targets *any* role, so through it the Next app is the right call, it matches the most reqs and already demos; doing the rewrite mid-search would trade applying-time for a half-migrated flagship that demos worse than the working one. The moment the job lands, that calculus flips and this is item one. **What can start now anyway:** casual Nuxt/Vue OSS contributions carry the specialist signal on their own and need no rewrite, so they can begin anytime; only the flagship rewrite waits. **Versioning:** by the mechanical test a rewrite that keeps the schema is not automatically a major, so this is not itself the `2.0.0`; it sits in the cluster because its trigger is the same date. The `positions` entity below is what forces the major.

Japanese applications conventionally want two documents: 履歴書 (personal history, a standardised form) and 職務経歴書 (career history, free-form). Generating both as PDFs from stored profile data would be the clearest possible signal that the author understands the market. 履歴書 alone is additive, but its twin *is* a `positions` table rendered as prose, and shipping half the pair, then maintaining a PDF toolchain for a year before the other half is even buildable, is the worst version of the trade. **Format question answered (2026-07-11):** the JIS template was indeed [withdrawn from the JIS standards in July 2020](https://japan-dev.com/blog/japanese-resume-rirekisho) (stationery stores still sell "JIS-compliant" pads, but it is a dead standard), and MHLW published a recommended replacement format (厚生労働省様式) designed for fair hiring: [gender optional; commute time, dependents, and spouse fields removed](https://www.gtalent.jp/blog/japanwork-en/job-hunting-en/rirekisho-en). **Target the MHLW format**: it is the closest thing to official, and its fair-hiring rationale is a good line in the README. **Carry cost (recorded 2026-07-11): the highest in this file.** PDF generation is a known maintenance sink (toolchain choice, CJK font embedding, layout drift), and on Cloudflare Workers (the centerpiece's runtime) it is further constrained to pure-JS/WASM libraries or an external rendering service, no native binary toolchain; the MHLW format itself can also churn. Highest wow, highest carry; scope it with both eyes open, the way the dark-mode decision (`CHANGELOG.md` § Decisions) weighed its cost side. **Storage of the pair is parked with it:** typed document slots for uploading a 履歴書/職務経歴書 alongside the English resume were considered for `v1.x` and deferred: more blobs on the pg_dump-backed database (the same cost the no-version-history decision refused) for documents whose real payoff arrives when generation ships. If uploads are wanted sooner, the shape is a typed `documents` table reusing the `v1.4.4` filename machinery, not more bytea columns.
