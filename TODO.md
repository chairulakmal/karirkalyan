## The rule: `v1` takes bug fixes only

**`v1.11.0` was the last feature release, and `v1.11.1` the last release of any kind: `v1` now ships untagged bug fixes and nothing else.** Three reasons, and the first decides it:

- **A `v1` feature is work with a scheduled deletion date.** `2.0.0`'s centerpiece is a ground-up rewrite onto Cloudflare (below): Rails becomes Hono, Next becomes Nuxt. Anything built in `api/` or `web/` from here has to be built a second time in a stack that does not exist yet, so it is paid for twice and demoed once.
- **The app is finished for the search that is actually running.** The north star is one user, and he has the tool: capture, pipeline, follow-ups, takeability constraints, the daily driver. Every remaining idea here pays off *after* the search closes, which is what the `2.0.0` trigger encodes.
- **Cadence.** Each PR burns two CI runs, and each merge adds a manual `bin/deploy` run to make (`CLAUDE.md` § Branching & PRs). A frozen feature surface is what makes the one-PR-per-day rule cheap instead of something to work around.

**The admission test, applied to anything proposed for `v1`:** does it make something the app already does work correctly, or stop something it already does from being abused? If yes it ships, and it is a patch by the mechanical test (no migration, no `v1` contract broken, no new capability). If it adds a capability, however small and however tempting, it is `2.0.0` work and waits for the trigger. Security fixes, dependency bumps, and CI chores pass on the same reading: none is a capability.

**Three exceptions have been taken, knowingly. The first is dashboard pins (2026-08-04).** Up to three applications hoisted to the top of the dashboard list, held in `localStorage` (`SPEC.md` § Pinned applications). It is a capability and it **fails the admission test above**; it was built because the author asked for it with the trade in front of him, not because an argument was found that let it through. It is recorded here so the freeze stays honest: a rule with an unrecorded exception is a rule nobody believes the second time. What it cost is bounded and worth naming, because that boundedness is the whole of its defence: no migration, no endpoint, no Rails file, and `web/`-only, which is also the code the rewrite deletes wholesale, so it is the *most* throwaway shape a feature can have. **This is not a precedent, and the test is unchanged.** The next feature is measured against the test, not against this paragraph.

**The second is the T1 type swap (2026-08-05).** The whole app moves from Fraunces + Manrope + IBM Plex Mono to Plus Jakarta Sans alone ([`BRAND.md`](BRAND.md) § Shipping T1). It adds no capability, so it does not fail the test the way pins did, but it does not pass it either, because only part of it is correctness. The defect is narrow: display-cut italic Fraunces was rendering at 20px in the dashboard and board card titles, where the joins go hairline and the italic `a` and `e` close up. Replacing three typefaces is a larger move than that defect required. The argument for the rest is that the brand book had already made the decision, and a mirror that disagrees with its source is the exact drift this project keeps paying for. Bounded the way pins were: `web/`-only, no migration, no endpoint, no Rails file, and `globals.css` is code the rewrite deletes wholesale. The same sentence applies: not a precedent, and the test is unchanged.

**The third is the screening success rate (2026-08-19).** A fourth stat card, and a fourth figure in the dashboard payload: the percent of applied applications that got past the 書類選考, which is `response_rate` with the rejections taken out (`SPEC.md` § The dashboard payload). It is a new capability and it **fails the admission test**, and it was asked for with the cost in this paragraph in front of the author. One thing separates it from the two above: it is the only exception so far that pays off *during* the search rather than after it, which is the second bullet of the rule met head-on. Response rate alone cannot tell a targeting problem (nobody is reading it) from a resume problem (they read it and said no), and those two have opposite remedies, so a search running right now is exactly when the figure is worth having. Its cost is also worse than the other two, which is worth naming rather than glossing: pins and T1 were both defended on being `web/`-only, the code the rewrite deletes wholesale, and this one is not. It touches `DashboardController`, the payload, `STATS_CACHE_VERSION`, the response schema and both locales, so Hono pays for it a second time. There is no migration: it is two counts over `timeline_entries`, which already hold the answer. **Not a precedent, and the test is unchanged.**

**The freeze does not gate the `2.0.0` cluster; it is what fills it.** What is frozen is shipping features into the current stack, not wanting them. An idea that arrives tomorrow gets written down there, not argued into a patch.

## Standing rules

Three rules that outlive the releases that produced them. The freeze retires the first two from `v1` duty (no patch adds a column or a field), so their live consumer is the `2.0.0` schema work and the record of why the existing columns are shaped as they are; other documents cite them here by name.

- **The trap that breaks a minor whenever it adds a column: the column must be nullable or defaulted.** A `NOT NULL` column with no default means the previous image's `INSERT`s fail against the new database, which by the mechanical test quietly turns a minor into a **major**: the only way a minor violates its own versioning. `v1.6.0`'s two new tables (`credentials`, `push_subscriptions`), `v1.8.0`'s eight `applications` columns, and `v1.9.0`'s visa/hiring/timezone fields all shipped clean under it. A column left loose is deferred, not forgotten: the `2.0.0` schema re-optimization item below owns the tightening pass, so the debt has an address.
- **Field admission test, for any new per-application column** (channel, agency, comp structure, language level, hiring entity, timezone, all of them): it must be **captured at prefill time by `UrlPrefillService`, or cost near-zero manual entry**. The app has one user, and a field he stops filling in after the fifth application is dead schema plus form friction. Bites next on `2.0.0`'s `positions` entity, the residents-only column, and the tightening pass.
- **Perishable-facts refresh rule, for every Japan-market item.** Each embeds perishable external facts: fee schedules, processing times, survey medians. A career tool that confidently states last year's rules is worse than one that says nothing, so each such item must state its **annual refresh cost** when it is scoped, and the sum of those lines is a real cap on how many a solo maintainer can ship. The shipped ones carry their cost already (the `holidays` gem is one `bundle update`; `Visa::COE_LEAD_TIME_DAYS` and the HSP point table are sourced constants). Governs the `2.0.0` career-intelligence item next, which already budgets one data-entry session a year.

### The centerpiece: rewrite to Hono + Nuxt on Cloudflare *(item one the moment the search succeeds)*

Decided 2026-07-22. What used to read as three scattered items (a Nuxt "north star", a Hono backend, a $0-hosting move off Railway) is **one move**: it settles three bets at once and they share a single trigger.

- **Specialty signal (the portfolio bet).** Depth over breadth: rather than staying one more generic Next.js tracker, lean all the way into the framework the author already contributes to, so the flagship app *is* the flagship of a Vue/Nuxt-specialist-and-OSS-contributor identity.
- **$0 hosting (the cost bet).** Railway has **no free tier** (Hobby is a $5/month minimum), so today's ~$6.30/month (api ~$4.40 of it at a 0.44 GB average, measured 2026-07-20) only zeroes by leaving Railway entirely, *both* services. This rewrite lands both halves on Cloudflare's free tier by construction. The always-warm-demo rationale (the repo's job is Tokyo hiring signal; its first hit is a screener clicking the link) expires the moment the job lands, and cost wins.
- **Serverless modernization.** Cold starts stop mattering once nobody is being impressed by a live demo, so the trade-offs that would hurt a portfolio piece are free here.

The target stack, verified free as of 2026-07-22:

- **Backend: Rails → Hono on Cloudflare Workers.** ActiveRecord is replaced by a TS query layer (Drizzle or Kysely over `pg`), so the schema survives but the ORM does not. Solid Queue's persistent poller moves to Cloudflare Cron Triggers. The two invariants port as *shape*, not as a rewrite of the rules: `ApplicationFSM::TRANSITIONS` stays the single copy of the transition table (now in TS), and status changes still route through one transition service, never direct attribute writes.
- **Frontend: Next → Nuxt.** The single largest work item in this file: all of `web/`, the i18n navigation wrapper, the CSP-nonce `proxy.ts` guard, every component and form. Nuxt/Nitro's **native Cloudflare preset** makes the deploy trivial and is the cleaner of the two paths, versus keeping Next behind the OpenNext `@opennextjs/cloudflare` adapter.
- **Data: Postgres stays, the host changes.** Neon or Supabase free tier, fronted by **Cloudflare Hyperdrive** (connection pooler + query cache: free, no egress charge, `node-postgres` its recommended driver, so the classic serverless connection-exhaustion problem is exactly what it absorbs). Two rejected paths, recorded so they are not re-litigated: **D1 is SQLite, not Postgres**, so it is no drop-in for this schema; and Cloudflare's *native* managed Postgres (via PlanetScale, billed through the Cloudflare account, June 2026) is **paid**, the convenience path rather than the free one.
- **Public domain: `kk.chairulakmal.com`** (decided 2026-07-22), bound to the Worker as a custom-domain route. A subdomain of the personal apex on purpose: it puts the author's name as the primary information in the link, so a screener sees whose project this is before the page loads, the signal a standalone `karirkalyan.com` would throw away. It is free and consistent with the $0 goal (one DNS record on a zone already run), and the terse `kk` beats a self-documenting `karirkalyan.` slug precisely to keep the name the dominant token. **Prerequisite, and the one thing that inverts the signal:** `chairulakmal.com` itself must resolve to a real personal site or CV, because a screener will strip `kk.` to see who the author is, and a parked or 404 apex reads worse than no custom domain at all. A dedicated product domain is warranted only on a pivot to external users, which the north star rejects.

**Why the trigger and not now:** the current search targets *any* role, so through it the Next app is the right call, matching the most reqs and already demoing; a rewrite mid-search trades applying-time for a half-migrated flagship that demos worse than the working one. The moment the job lands that flips and this is item one. **What can start now anyway:** casual Nuxt/Vue OSS contributions carry the specialist signal on their own, so only the flagship rewrite waits. **Versioning:** a rewrite that keeps the schema is not automatically a major, so this is not itself the `2.0.0`; it sits in the cluster because its trigger is the same date. The `positions` entity forces the major.

### The rest of the cluster

- [ ] **`positions` (tenure) entity: the keystone; design it before building anything below.** *(the only major in this file)* Today `accepted` is a terminal status; a career tracker needs the job you then held as a first-class thing: company, title, start/end, and the comp structure `v1.8.0` shipped (normalized 年収). Comp history across positions (benchmarkable against the TokyoDev medians cited below), resume versioning, internal-promotion stages, and 職務経歴書 generation all hang off it: a 職務経歴書 is a positions table rendered as prose. Write it into SPEC.md's data model **first**; retrofitting later means migrating what `accepted` means. **Scoping trigger: accepting an offer**, not finishing a prior release: the moment the search succeeds is the moment this entity is needed, or the app exits the user's life exactly when its retention story was supposed to begin.
- [ ] **Make the app survive its own success** *(every sub-item hangs off `positions`)*. Today the lifecycle ends at `accepted`: the search closes and there is no reason to open the app again until the next one. Extend it into the tenure _between_ searches, so landing a job is a state change, not an exit:
  - **Resume as a living document**: the resume is already stored per application; add a current, versioned profile that keeps improving while employed, so the next application starts from the best version rather than a year-old PDF. Feeds the generation item below.
  - **Low-noise market watch**: `wishlist` already models "interesting, not applied"; let it be the employed-mode default. Tracking relevant roles while happily employed is how you know your market value and when to move.
  - **Skills & certs against the market, not a wishlist**: `UrlPrefillService` already reads postings with Claude; extract the skills and certifications each tracked role asks for at prefill time, and the gap against what the profile holds becomes a ranked "learn next" list (JLPT level, cloud certs, a framework) with zero extra data entry. Goals can target the current employer too: an internal promotion has stages like an application does.
  - **Periodic check-ins**: a recurring job and a mailer exist (whatever they are called after the rewrite); a quarterly "update your resume, review your goals" nudge is one more of them, with the same dead-zone awareness as the calendar-aware follow-ups in `v1.4.0`.

  This repositions the tracker from a search tool you abandon on success into a career companion with a retention story, and it is the better portfolio argument too, since every sub-item reuses machinery that already exists (blob storage, `wishlist`, prefill extraction, recurring jobs) rather than demanding new infrastructure.

  **Scope boundary:** career growth does **not** mean drifting into a **networking CRM**, a **habit tracker**, or a **learning tracker**. Those are separate products with mature incumbents, and a broad-shallow app is a worse portfolio piece than a narrow-deep one. The admission test for any career-growth feature: **it must reuse the FSM, the timeline, the prefill extraction, or the `positions` entity**; if it needs none of them, it belongs in a different app. Concretely: contacts go no further than the `agencies` table (which models submission ownership, not relationships); skills/certs/JLPT go no further than the prefill-derived gap list (a ranked "learn next", never course progress or streaks); check-ins stay a recurring nudge, never a journaling habit loop.

- [ ] **`companies` and `company_groups`: make the employer a thing rather than a string** *(wanted 2026-08-04; design it alongside `positions`, ship it with or before)*. `applications.company` is a `string, null: false` today, so every fact about an employer that outlives a single application has nowhere to live: it gets retyped, or lost. Three such facts are wanted first, and they are the ones the search actually turns on. **The reapplication window:** how long after a rejection this employer will look at you again, commonly six or twelve months in Japan, and sometimes shared across a whole group. **The language situation of the team you would actually sit in:** a different fact from `japanese_level`, which records what the *posting demands*; this records what the team runs on day to day, meaning standup and code-review language, and whether the English is one accommodating manager or the whole floor. **What kind of company it is at all:** whether the row is the employer you would work for, or a 派遣会社 or SES vendor that employs you and places you in someone else's office. All three are learned in interviews rather than read off postings, which is precisely why they need an employer-shaped home instead of another `applications` column.
  - **Shape: `companies`, one-to-many under a nullable `company_groups`.** `companies` mirrors `agencies` (per-user, unique on `(user_id, name)`, nullable FK from `applications`), with `applications.company_id` replacing the string, and `positions.company_id` pointing at the same table rather than duplicating the employer as free text a second time. The group is nullable because most employers are not in one, and it exists to answer exactly one question: *I was rejected by X, does that touch Y?* Group-wide reapplication windows and shared ATSes are real in Japanese conglomerates, so the window lives on both levels, the company's own value falling back to its group's, and the board says so when a sibling is already on it.
  - **Company kind (事業会社 vs 客先常駐) is unrecorded anywhere in `v1`, and it is a company fact, which is the sharpest argument for the table.** Nothing today comes close to it: `channel` (`direct`/`agent`/`referral`) says how the posting reached the user, `agency_id` says who owns the submission, and `hiring_entity` says how a Japan resident can be employed at all. A 客先常駐 posting reads perfectly ordinary on all three. Propose the enum on the axis that decides a career rather than the one that decides a contract, meaning whose product you build and who directs your work: `employer` (事業会社, its own product), `haken` (派遣, the vendor employs you and the client directs you, with the 3-year rule and the rest of what 派遣法 attaches), `ses` (準委任 / 客先常駐, the vendor holds the contract and you still sit at the client), `jutaku` (受託開発, client projects done at the vendor's own office). **Whether `haken` and `ses` stay separate is the one call to make when scoping:** the legal difference is 指揮命令権 and it is real, but the career difference between them is thinner than the legal one, and a two-value 事業会社 / 客先 split may carry the whole signal at a quarter of the taxonomy.
    - **Not a fifth `hiring_entity` value.** That column asks whether a company can employ a Japan resident and through what vehicle, aimed at foreign employers with no Japan entity; a 派遣会社 answers `own_entity`, truthfully and uselessly. Folding the two repeats the sponsorship-versus-residency collapse the 2026-08-03 prefill fix removed, one layer down.
    - **It interacts with the other two facts, which is why they want one row.** A 派遣会社 has no meaningful reapplication window, since it takes you back whenever it has a seat, and its language situation is not its own but the client's. So for `haken` and `ses` the English-friendliness field is honestly unanswerable at company level, and the UI should say that rather than collect a lie. *Which* client the user actually sat at is a `positions` fact, because a tenure at one of these firms is a sequence of placements, not one job.
    - **Prefill can usually tell, and must be allowed to say it cannot.** The tells are in the text (派遣, 準委任, 客先常駐, プライム, 二次請け), and the loudest one is negative space: 大手IT企業でのシステム開発 that never names the company. Same rule as `sponsorship`, for the same reason it was learned the hard way: a wrong guess here is worse than an empty field, so unrecorded stays the default and the tells go in the tool-schema description explicitly.
    - **`agencies` and `companies` will sometimes name the same firm, and that is fine.** Persol and Recruit run 人材紹介 and 派遣 arms at once, so one real-world company can be an `agencies` row (it submitted the user somewhere) and a `companies` row (it would employ them). Keep the tables separate: `agencies` exists for submission ownership and is a name vocabulary, so merging them buys a harder migration in exchange for a coincidence. Revisit only if `company_groups` turns out to want agencies as members.
  - **The window is computed, not entered twice.** `rejected → applied` is already an FSM edge and `timeline_entries` already dates the rejection, so "eligible again on <date>" is a query over machinery that exists, plus a warning when a reapplication is opened early and a nudge when the window opens. Reusing the FSM and the timeline is how this clears the career-growth scope boundary above.
  - **Auto-create the company when the application is created**, from the name `UrlPrefillService` already extracts. That is what keeps the common path inside the field admission test: no new form field, no new prefill work. **The cost is deduplication, and it is the real work:** "Google Japan", "Google Japan G.K." and "グーグル合同会社" find-or-create three rows against a naive unique index. `agencies` carries that same trap today at a scale where it never bites; a table fed by every application creation is not that scale. Normalise to a canonical key on create and give the user a merge, or the table becomes the free-text field it replaced, wearing a join.
  - **Manual entry is honest here in a way it is not per-application.** The window and the language situation are typed once per employer and read by every application to it, so the fifth application to the same company costs nothing. That amortisation is what the field admission test is really asking about, and it is why these two facts would fail the test as `applications` columns and pass it as `companies` columns.
  - **Versioning:** swapping `company` for `company_id` is a backfill plus a backward-incompatible migration, free only in a major, so it belongs in the same pass as the schema debt below rather than being paid for twice.

- [ ] **Let the user edit the ghost-risk thresholds from the settings page** *(wanted 2026-08-03; `api/app/queries/applications/ghost_risk_query.rb`, `web/app/[locale]/(app)/settings/`)*. The 2026-08-03 fix took the half of this that was a fix: silence is counted in business days now, and the derived p90 is gone in favour of a stated policy, `THRESHOLDS` of 15 business days on `applied` and 10 on `phone_screen`. What is left is the genuinely new part, editing those two numbers without a deploy. **A capability, and a smaller one than before:** the constant is already the whole mechanism, so this is a `users` migration for two nullable integer overrides, a `PATCH /me` widening beside the residence fields, a settings card next to residence and passkeys, and two message catalogs. Null means "use the constant", so the shipped policy stays the default rather than becoming a fallback. **Keep a clamp on the manual path** (the removed one was 7 to 90 calendar days): a typo'd 1-day threshold flags the entire board, and the reason the old floor existed survives its cause.

- [ ] **Model "residents of Japan only" as its own fact, and filter on it** *(wanted 2026-08-03; the other half of the `v1` prefill bug above)*. That fix only stops the extractor lying; it leaves the residency requirement recorded nowhere. For this user it is the most useful filter on the board, and it points the *opposite* way to how the app treats it today: as a dependent already living in Tokyo he competes in a candidate pool less than half the size of the one for postings open to overseas applicants, so residents-only listings are where his odds are best and should be surfaced, not buried. **Not a fourth `sponsorship` value:** the axes are orthogonal (a residents-only role may or may not sponsor; a role open to overseas candidates may sponsor nothing), so folding them re-creates the collapse the `v1` fix removes, one layer down, and `hiring_entity`'s `unsupported` is a third axis again (can the company employ someone in Japan at all). So: a new per-application column plus a filter, a capability and an additive widening of the index contract. It **passes the field admission test** through the prefill door, since postings state residency plainly in the sentence the extractor already reads. Land it with the schema pass below, so the column starts tight.

- [ ] **Career intelligence: benchmark reports from published surveys** *(its headline view, comp percentile for the current position, needs `positions`. The offer-comp-vs-median slice became buildable when `v1.8.0` landed the 年収 structure, but stays bundled here: no annual refresh-cost commitment before `positions` makes the full view buildable.)* An in-app, yearly-refreshed summary of reliable market sources: the [TokyoDev annual survey](https://www.tokyodev.com/articles/the-2025-tokyodev-developer-survey-results-are-live) first (2025: 989 respondents; median ¥9.5M, split by employer type, experience band, and language use), with MHLW's official wage statistics (賃金構造基本統計調査) as the government counterpart. The point is not the report (a static summary page would fail the career-growth admission test) but the user's own data shown against it: comp percentile for the current position (needs `positions`), offer comp vs the market median for his experience band at decision time, his Japanese level against the language-requirement distribution of the roles he tracks. Implementation is a versioned reference dataset (a seed file refreshed once per survey cycle, no scraping, no pipeline), so the recurring cost is one data-entry session a year. Check each source's licensing and attribution terms before shipping its numbers.
- [ ] **Settle the `v1.x` schema debt in the first major: re-optimize every table change the minor releases were forced to leave loose** *(stays standalone in this cluster; rides whichever major actually ships, because a major is the only release where a backward-incompatible migration is free)*. The nullable-or-defaulted standing rule is a deliberate trade, minor-release safety then for schema looseness now, and this is where the bill gets settled. **The freeze fixes the size of that bill:** no future `v1` release adds a column, so what needs tightening is exactly what shipped through `v1.11.0`. The pass, table by table (`credentials` and `push_subscriptions` from `v1.6.0`, the eight nullable `applications` columns from `v1.8.0`, the visa/hiring/timezone fields from `v1.9.0`): backfill and tighten to `NOT NULL` or a real default wherever the domain requires the value, promote free-text columns to check-constrained enums where the value set has proven closed, add the indexes deferred on growth grounds, and drop any column the field admission test killed in use, since a field the user stopped filling is dead schema and the major is the one chance to delete it cheaply. **The `timeline_entries` offer-lookup index is off this list: it shipped on 2026-08-05** and is no longer owed here. It was parked for the major on the grounds that a personal-scale timeline is a few hundred rows, which was the wrong reading of why the read was slow. The cost was never the row count: `avg_days_to_offer`'s `DISTINCT ON` carried no user predicate, so a per-user endpoint scanned and sorted **every** account's rows, and the stats cache keys on `MAX(updated_at)`, so any edit to any application sent the next dashboard back through it. Scoping the subquery was the fix; `index_timeline_entries_on_offer`, partial on `(application_id, created_at) WHERE to_status = 'offer'`, is what serves it (`SPEC.md` § `timeline_entries`). A plain index on `to_status` is still not wanted, for the reason it never was: `'offer'` is the only value any query names. One exception so the pass does not over-tighten: sponsorship stays nullable by design, because unknown is decision-relevant signal, not missing data (`v1.9.0`'s admission-test note is the record). Since the Hono rewrite comes first, the tightening applies under the TS query layer rather than ActiveRecord, unchanged in substance: a loose schema under a new runtime is the same debt wearing a different API.
- [ ] **Rirekisho + shokumu-keirekisho generation** *(deliberately parked past the rest of the cluster; ship both together, after `positions`)*. Japanese applications conventionally want two documents: 履歴書 (personal history, a standardised form) and 職務経歴書 (career history, free-form). Generating both as PDFs from stored profile data would be the clearest possible signal that the author understands the market. 履歴書 alone is additive, but its twin *is* a `positions` table rendered as prose, and shipping half the pair, then maintaining a PDF toolchain for a year before the other half is buildable, is the worst version of the trade. **Format question answered (2026-07-11):** the JIS template was [withdrawn from the JIS standards in July 2020](https://japan-dev.com/blog/japanese-resume-rirekisho) (stationery stores still sell "JIS-compliant" pads, but it is a dead standard), and MHLW published a recommended replacement (厚生労働省様式) designed for fair hiring: [gender optional; commute time, dependents, and spouse fields removed](https://www.gtalent.jp/blog/japanwork-en/job-hunting-en/rirekisho-en). **Target the MHLW format**: it is the closest thing to official, and its fair-hiring rationale is a good line in the README. **Carry cost (recorded 2026-07-11): the highest in this file.** PDF generation is a known maintenance sink (toolchain choice, CJK font embedding, layout drift), and on Cloudflare Workers it is further constrained to pure-JS/WASM libraries or an external rendering service, no native binary toolchain; the MHLW format itself can also churn. Highest wow, highest carry; scope it with both eyes open, the way the dark-mode decision (`CHANGELOG.md` § Decisions) weighed its cost side. **Storage of the pair is parked with it:** typed document slots for uploading a 履歴書/職務経歴書 alongside the English resume were considered for `v1.x` and deferred, being more blobs on the pg_dump-backed database (the cost the no-version-history decision refused) for documents whose real payoff arrives when generation ships. If uploads are wanted sooner, the shape is a typed `documents` table reusing the `v1.4.4` filename machinery, not more bytea columns.
