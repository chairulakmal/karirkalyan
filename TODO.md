## The rule: `v1` takes bug fixes only

**`v1.11.0` was the last feature release, and there will be no `v1.12.0`: every remaining `v1` release is a patch.** Three reasons, and the first decides it:

- **A `v1` feature is work with a scheduled deletion date.** `2.0.0`'s centerpiece is a ground-up rewrite onto Cloudflare (below): Rails becomes Hono, Next becomes Nuxt. Anything built in `api/` or `web/` from here has to be built a second time in a stack that does not exist yet, so it is paid for twice and demoed once.
- **The app is finished for the search that is actually running.** The north star is one user, and he has the tool: capture, pipeline, follow-ups, takeability constraints, the daily driver. Every remaining idea here pays off *after* the search closes, which is what the `2.0.0` trigger encodes.
- **Cadence.** Every merge under a watch path is a Railway deploy, and each PR burns two CI runs (`CLAUDE.md` § Branching & PRs). A frozen feature surface is what makes the one-PR-per-day rule cheap instead of something to work around.

**The admission test, applied to anything proposed for `v1`:** does it make something the app already does work correctly, or stop something it already does from being abused? If yes it ships, and it is a patch by the mechanical test (no migration, no `v1` contract broken, no new capability). If it adds a capability, however small and however tempting, it is `2.0.0` work and waits for the trigger. Security fixes, dependency bumps, and CI chores pass on the same reading: none is a capability.

**The freeze does not gate the `2.0.0` cluster; it is what fills it.** What is frozen is shipping features into the current stack, not wanting them. An idea that arrives tomorrow gets written down there, not argued into a patch.

## Standing rules

Three rules that outlive the releases that produced them. The freeze retires the first two from `v1` duty (no patch adds a column or a field), so their live consumer is the `2.0.0` schema work and the record of why the existing columns are shaped as they are; other documents cite them here by name.

- **The trap that breaks a minor whenever it adds a column: the column must be nullable or defaulted.** A `NOT NULL` column with no default means the previous image's `INSERT`s fail against the new database, which by the mechanical test quietly turns a minor into a **major**: the only way a minor violates its own versioning. `v1.6.0`'s two new tables (`credentials`, `push_subscriptions`), `v1.8.0`'s eight `applications` columns, and `v1.9.0`'s visa/hiring/timezone fields all shipped clean under it. A column left loose is deferred, not forgotten: the `2.0.0` schema re-optimization item below owns the tightening pass, so the debt has an address.
- **Field admission test, for any new per-application column** (channel, agency, comp structure, language level, hiring entity, timezone, all of them): it must be **captured at prefill time by `UrlPrefillService`, or cost near-zero manual entry**. The app has one user, and a field he stops filling in after the fifth application is dead schema plus form friction. Bites next on `2.0.0`'s `positions` entity, the residents-only column, and the tightening pass.
- **Perishable-facts refresh rule, for every Japan-market item.** Each embeds perishable external facts: fee schedules, processing times, survey medians. A career tool that confidently states last year's rules is worse than one that says nothing, so each such item must state its **annual refresh cost** when it is scoped, and the sum of those lines is a real cap on how many a solo maintainer can ship. The shipped ones carry their cost already (the `holidays` gem is one `bundle update`; `Visa::COE_LEAD_TIME_DAYS` and the HSP point table are sourced constants). Governs the `2.0.0` career-intelligence item next, which already budgets one data-entry session a year.

- [ ] **`next dev` crashes even with a 4 GB heap** (`--max-old-space-size=4096`, added in v1.1.1). **Diagnosed 2026-07-11:** a **V8 heap leak in the `next-server` process**, not native/Rust memory and not the OS. Journal shows zero OOM-killer and zero systemd-oomd kills: 30 days at diagnosis, **re-verified over 60 days on 2026-08-03**. **Beware the obvious grep, which reads the exact opposite way.** `journalctl | grep -iE 'out of memory|oom-kill|oomd'` returns **293 hits and zero events**, because the `systemd-oomd` unit's own description is "Userspace Out-Of-Memory (OOM) Killer", so every start, stop, socket, and accounting line repeats the phrase; the count factors as 8 lifecycle line-types across 33 boots, plus 29 `Consumed … CPU time` and `Deactivated successfully` lines. The command that actually answers the question is `journalctl -k | grep -cE 'oom-kill:|Killed process'`, which returns **0**. An instrumented run (`--report-on-signal` diagnostic reports + RSS sampling) showed V8 `usedMemory` tracking RSS growth ~1:1 while the native baseline stayed a flat ~0.8–1.5 GB. Retention is monotonic and unbounded: ~239 MB V8 heap at boot, ~541 MB after warming the ten public routes, then **~40–60 MB retained per HMR rebuild** (3.1 GB used / 5.8 GB RSS after 30 scripted edits, `detachedContextCount` 0 throughout). Matches upstream discussion **#93451** (unbounded growth after HMR edits, ~7 GB, still open and unresolved as of 2026-08-03); issue #85290 (404 → infinite compile loop) does **not** reproduce here. Warm boot-to-ready is ~5 s with the Turbopack FS cache, so a periodic restart is a viable stopgap.
  - **Status 2026-08-03: quiet, not fixed.** No `*.heapsnapshot` exists anywhere in the repo, so the near-heap-limit trigger has not fired once since `cf7cd8d` (2026-07-11). That is the expected reading, not a surprise: the ceiling doubled, retention is per-HMR-rebuild at ~40–60 MB, and almost no front-end editing happened in that window, so zero crashes follows without a single byte of the leak being fixed. It will return on the first day of real `web/` work. (A live server sampled that day sat at 826 MB RSS five minutes after boot, already above the ~541 MB warm baseline.)
  - **Next actions: file upstream now; stop waiting for the snapshot.** The stopgap is **done** (`cf7cd8d`), and the dev script runs with an 8 GB heap and `--heapsnapshot-near-heap-limit=1` (allowed there; `--trace-gc` is not), so a real crash still writes the snapshot. KarirKalyan's long-term identity is a **career growth tracker**, not just an application tracker; the name already says so (karir = career, so the product is currently narrower than its own name). **The centerpiece, decided 2026-07-22, is a ground-up rewrite onto Cloudflare: the Rails API becomes a Hono app on Workers, the Next.js frontend becomes Nuxt.** The app stops being a portfolio piece built to impress screeners and becomes the author's own career pet project, rebuilt in his specialty (Vue/Nuxt); everything else in this cluster is what that rewritten app then holds. ### The centerpiece: rewrite to Hono + Nuxt on Cloudflare *(item one the moment the search succeeds)*

Decided 2026-07-22. What used to read as three scattered items (a Nuxt "north star", a Hono backend, a $0-hosting move off Railway) is **one move**: it settles three bets at once and they share a single trigger.

- **Specialty signal (the portfolio bet).** Depth over breadth: rather than staying one more generic Next.js tracker, lean all the way into the framework the author already contributes to, so the flagship app *is* the flagship of a Vue/Nuxt-specialist-and-OSS-contributor identity.
- **$0 hosting (the cost bet).** Railway has **no free tier** (Hobby is a $5/month minimum), so today's ~$6.30/month (api ~$4.40 of it at a 0.44 GB average, measured 2026-07-20) only zeroes by leaving Railway entirely, *both* services. This rewrite lands both halves on Cloudflare's free tier by construction. The always-warm-demo rationale (the repo's job is Tokyo hiring signal; its first hit is a screener clicking the link) expires the moment the job lands, and cost wins.
- **Serverless modernization.** Cold starts stop mattering once nobody is being impressed by a live demo, so the trade-offs that would hurt a portfolio piece are free here.

The target stack, verified free as of 2026-07-22:

- **Backend: Rails → Hono on Cloudflare Workers.** ActiveRecord is replaced by a TS query layer (Drizzle or Kysely over `pg`), so the schema survives but the ORM does not. Solid Queue's persistent poller moves to Cloudflare Cron Triggers. The two invariants port as *shape*, not as a rewrite of the rules: `ApplicationFSM::TRANSITIONS` stays the single copy of the transition table (now in TS), and status changes still route through one transition service, never direct attribute writes.
- **Frontend: Next → Nuxt.** The single largest work item in this file: all of `web/`, the i18n navigation wrapper, the CSP-nonce `proxy.ts` guard, every component and form. Nuxt/Nitro's **native Cloudflare preset** makes the deploy trivial and is the cleaner of the two paths, versus keeping Next behind the OpenNext `@opennextjs/cloudflare` adapter.
- **Data: Postgres stays, the host changes.** Neon or Supabase free tier, fronted by **Cloudflare Hyperdrive** (connection pooler + query cache: free, no egress charge, `node-postgres` its recommended driver, so the classic serverless connection-exhaustion problem is exactly what it absorbs). Two rejected paths, recorded so they are not re-litigated: **D1 is SQLite, not Postgres**, so it is no drop-in for this schema; and Cloudflare's *native* managed Postgres (via PlanetScale, billed through the Cloudflare account, June 2026) is **paid**, the convenience path rather than the free one.
- **Public domain: `kk.chairulakmal.com`** (decided 2026-07-22), bound to the Worker as a custom-domain route. A subdomain of the personal apex on purpose: it puts the author's name as the primary information in the link, so a screener sees whose project this is before the page loads, the signal a standalone `karirkalyan.com` would throw away. It is free and consistent with the $0 goal (one DNS record on a zone already run), and the terse `kk` beats a self-documenting `karirkalyan.` slug precisely to keep the name the dominant token. **Prerequisite, and the one thing that inverts the signal:** `chairulakmal.com` itself must resolve to a real personal site or CV, because a screener will strip `kk.` to see who the author is, and a parked or 404 apex reads worse than no custom domain at all. A dedicated product domain is warranted only on a pivot to external users, which the north star rejects.

**Why the trigger and not now:** the current search targets *any* role, so through it the Next app is the right call, matching the most reqs and already demoing; a rewrite mid-search trades applying-time for a half-migrated flagship that demos worse than the working one. The moment the job lands that flips and this is item one. **What can start now anyway:** casual Nuxt/Vue OSS contributions carry the specialist signal on their own, so only the flagship rewrite waits. **Versioning:** a rewrite that keeps the schema is not automatically a major, so this is not itself the `2.0.0`; it sits in the cluster because its trigger is the same date. The `positions` entity forces the major.

### The rest of the cluster

- [ ] **`positions` (tenure) entity: the keystone; design it before building anything below.** *(the only major in this file)* Today `accepted` is a terminal status; a career tracker needs the job you then held as a first-class thing: company, title, start/end, and the comp structure `v1.8.0` shipped (normalized 年収). Comp history across positions (benchmarkable against the TokyoDev medians cited below), resume versioning, internal-promotion stages, and 職務経歴書 generation all hang off it: a 職務経歴書 is a positions table rendered as prose. Write it into SPEC.md's data model **first**; retrofitting later means migrating what `accepted` means. **Scoping trigger: accepting an offer**, not finishing a prior release: the moment the search succeeds is the moment this entity is needed, or the app exits the user's life exactly when its retention story was supposed to begin.
- [ ] **Make the app survive its own success** *(every sub-item hangs off `positions`)*. Today the lifecycle ends at `accepted`: the search closes and there is no reason to open the app again until the next one. Extend it into the tenure _between_ searches, so landing a job is a state change, not an exit:
  - **Resume as a living document**: the resume is already stored per application; add a current, versioned profile that keeps improving while employed, so the next application starts from the best version rather than a year-old PDF. Feeds the generation item below.
  - **Low-noise market watch**: `wishlist` already models "interesting, not applied"; let it be the employed-mode default. Tracking relevant roles while happily employed is how you know your market value and when to move.
  - **Skills & certs against the market, not a wishlist**: `UrlPrefillService` already reads postings with Claude; extract the skills and certifications each tracked role asks for at prefill time, and the gap against what the profile holds becomes a ranked "learn next" list (JLPT level, cloud certs, a framework) with zero extra data entry. Goals can target the current employer too: an internal promotion has stages like an application does.
  - **Periodic check-ins**: a recurring job and a mailer exist (whatever they are called after the rewrite); a quarterly "update your resume, review your goals" nudge is one more of them, with the same dead-zone awareness as the calendar-aware follow-ups in `v1.4.0`.

  This repositions the tracker from a search tool you abandon on success into a career companion with a retention story, and it is the better portfolio argument too, since every sub-item reuses machinery that already exists (blob storage, `wishlist`, prefill extraction, recurring jobs) rather than demanding new infrastructure.

  **Scope boundary:** career growth does **not** mean drifting into a **networking CRM**, a **habit tracker**, or a **learning tracker**. Those are separate products with mature incumbents, and a broad-shallow app is a worse portfolio piece than a narrow-deep one. The admission test for any career-growth feature: **it must reuse the FSM, the timeline, the prefill extraction, or the `positions` entity**; if it needs none of them, it belongs in a different app. Concretely: contacts go no further than the `agencies` table (which models submission ownership, not relationships); skills/certs/JLPT go no further than the prefill-derived gap list (a ranked "learn next", never course progress or streaks); check-ins stay a recurring nudge, never a journaling habit loop.

- [ ] **Let the user set the ghost-risk threshold himself, on the settings page** *(wanted 2026-08-03; `api/app/queries/applications/ghost_risk_query.rb`, `web/app/[locale]/(app)/settings/`)*. Both thresholds are derived and he has no say in either: `GhostRiskQuery` uses his own p90 once a stage has five completed responses, falls back to `DEFAULT_P90` (21 days on `applied`, 14 on `phone_screen`), and clamps to 7–90 days. Nowhere can he assert "three weeks of silence is ghosted, whatever my history says". **A capability, not a fix:** nothing is broken, the derived thresholds are the documented design (SPEC.md § `Applications::GhostRiskQuery`), and wanting control over a number is not the same as the number being wrong. The settings page being an obvious home does not make it small: a `users` migration, a `PATCH /me` widening, a settings card, two message catalogs. **Shape:** a per-stage override on `users`, null meaning "keep deriving" so the derived path stays the default rather than a fallback; served and written through `PATCH /me` beside the residence fields; a third settings card next to residence and passkeys; `GhostRiskQuery` reads the override ahead of the p90 and reports `basis: "manual"`, so the UI keeps explaining a number this consequential. Keep the 7–90 clamp on the manual path: a typo'd 1-day threshold flags the whole board.

- [ ] **Model "residents of Japan only" as its own fact, and filter on it** *(wanted 2026-08-03; the other half of the `v1` prefill bug above)*. That fix only stops the extractor lying; it leaves the residency requirement recorded nowhere. For this user it is the most useful filter on the board, and it points the *opposite* way to how the app treats it today: as a dependent already living in Tokyo he competes in a candidate pool less than half the size of the one for postings open to overseas applicants, so residents-only listings are where his odds are best and should be surfaced, not buried. **Not a fourth `sponsorship` value:** the axes are orthogonal (a residents-only role may or may not sponsor; a role open to overseas candidates may sponsor nothing), so folding them re-creates the collapse the `v1` fix removes, one layer down, and `hiring_entity`'s `unsupported` is a third axis again (can the company employ someone in Japan at all). - [ ] **Career intelligence: benchmark reports from published surveys** *(its headline view, comp percentile for the current position, needs `positions`. - [ ] **Settle the `v1.x` schema debt in the first major: re-optimize every table change the minor releases were forced to leave loose** *(stays standalone in this cluster; rides whichever major actually ships, because a major is the only release where a backward-incompatible migration is free)*. - [ ] **Rirekisho + shokumu-keirekisho generation** *(deliberately parked past the rest of the cluster; ship both together, after `positions`)*. Japanese applications conventionally want two documents: 履歴書 (personal history, a standardised form) and 職務経歴書 (career history, free-form). Generating both as PDFs from stored profile data would be the clearest possible signal that the author understands the market. 履歴書 alone is additive, but its twin *is* a `positions` table rendered as prose, and shipping half the pair, then maintaining a PDF toolchain for a year before the other half is buildable, is the worst version of the trade. **Format question answered (2026-07-11):** the JIS template was [withdrawn from the JIS standards in July 2020](https://japan-dev.com/blog/japanese-resume-rirekisho) (stationery stores still sell "JIS-compliant" pads, but it is a dead standard), and MHLW published a recommended replacement (厚生労働省様式) designed for fair hiring: [gender optional; commute time, dependents, and spouse fields removed](https://www.gtalent.jp/blog/japanwork-en/job-hunting-en/rirekisho-en). **Target the MHLW format**: it is the closest thing to official, and its fair-hiring rationale is a good line in the README. **Carry cost (recorded 2026-07-11): the highest in this file.** PDF generation is a known maintenance sink (toolchain choice, CJK font embedding, layout drift), and on Cloudflare Workers it is further constrained to pure-JS/WASM libraries or an external rendering service, no native binary toolchain; the MHLW format itself can also churn. Highest wow, highest carry; scope it with both eyes open, the way the dark-mode decision (`CHANGELOG.md` § Decisions) weighed its cost side. **Storage of the pair is parked with it:** typed document slots for uploading a 履歴書/職務経歴書 alongside the English resume were considered for `v1.x` and deferred, being more blobs on the pg_dump-backed database (the cost the no-version-history decision refused) for documents whose real payoff arrives when generation ships. If uploads are wanted sooner, the shape is a typed `documents` table reusing the `v1.4.4` filename machinery, not more bytea columns.
